# CLAUDE.md — Start Here

This is the base file for this project. **Always read this file first**, at the start of every session, before touching anything else.

## What to do after reading this file

1. Read `project.json` — full project data: structure, files, and the functions they contain. Use it as an index to find where something lives.
2. Read `action-map.json` — the full history of actions taken against user requirements, so past work isn't repeated or lost.
3. Do **not** read entire project files by default. Use `project.json` to locate the specific file/function you need, then read only that.
4. If a task touches a feature, check `features/` for its md file before starting — it may already document current behavior, open issues, or prior decisions.
5. If a task is similar to something done before, check `knoladge/` for how it was implemented last time (including any past failures) before redoing the research.

## Update rules (do these every time you make a change)

- **action-map.json**: append an entry for every action taken, tied to the user requirement that triggered it.
- **project.json**: update whenever files/functions are added, removed, or change purpose.
- **features/\<feature\>.md**: create one file per complete feature (not per small edit). Update the relevant feature file whenever that feature changes. A feature file should describe the whole feature, not just the latest tweak.
- **knoladge/**: document how something was implemented and what was learned, so it can be reused next time. Document failures and errors too — what went wrong and how (or whether) it was resolved.
- **Theme version**: every time you change anything in the theme (code, styling, assets — not just this doc system), bump the version in **all three** places that hold a copy of it: `style.css`'s `Version:` header, `functions.php`'s `HEX_VERSION` constant, and `tests/bootstrap.php`'s `HEX_VERSION` define (the test suite runs without loading `functions.php`, so it keeps its own copy — `tests/ThemeFilesTest.php` will fail if this one drifts from `style.css`). A docs-only change (editing `claude.md`/`project.json`/`action-map.json`/`features/`/`knoladge/` with no theme file touched) doesn't need a bump.
- **Scope discipline — main theme vs. child theme**: when the user's request is explicitly scoped to "the child theme" or "the main theme" (either by name or by clear context), confine all changes to that scope only. Don't touch the other one's files, settings, options, or behavior as a side effect — e.g. a child-theme-scoped request shouldn't modify `inc/updater.php`, the main `hex_updates` settings group, or any front-end/main-admin file, and vice versa. If a change genuinely needs to touch both, say so explicitly before doing it rather than silently expanding scope.

- **Font-size tokens (h1-h6/body/lead/large/small/meta) — strict rules, always follow**: explicit user correction after repeated clamp/sync confusion (*"why the font sizes in css file and theme options doesnt sync, they are differnt. always it should be same and always has to use theme option values and custom classes. not allowed to use only variable values directly"*).
  1. **Never a bare/hardcoded font-size — always Theme Options, always through a class.** Every font-size applied to markup must resolve through a Theme-Options-backed custom property, consumed only via its designated class: `.hex-h1`…`.hex-meta` (`assets/css/src/site-theme.css`, each class sets its own `--mobile-font-size: var(--hex-{key}-size-mobile, {default})` / `--desktop-font-size: var(--hex-{key}-size-desktop, {default})`, consumed by the one shared `clamp()` rule in rule 5 below) or the Tailwind-generated `.text-h1` etc. (`--text-{key}: var(--hex-{key}-size, {default})`). Never write a raw `font-size: 32px;` on an element, and never reference `--mobile-font-size`/`--desktop-font-size`/`--hex-h1-size-desktop`/etc. directly on any selector other than its own class — add the class instead. This is what makes a Theme Options edit (e.g. "H2 Desktop Size") actually apply everywhere that size is used.
  2. **The CSS fallback default and the PHP schema default must always be the identical literal.** The flat px fallback in `site-theme.css` for a token (both the `.hex-*` `:root` block and the `--text-*` `@theme` block) and that token's default in `hex_get_style_schema()` (`inc/style-settings.php`) must match exactly. Whenever one changes, change the other in the same edit — never let them drift.
  3. **A saved Theme Options value legitimately differing from the CSS default is not a bug** — it's an admin-configured override doing its job, and always wins (see `hex_get_style_value()`). If a `.hex-*`/`.text-*` size looks "unsynced" from what's in `site-theme.css`, check `{child theme}/theme-options.css` for a saved `--hex-{key}-size-desktop` first — that's almost always the explanation, not a code defect.
  4. **`--text-h1` etc. (bare h1-h6, `.text-h1`, `.prose`) and the PHP runtime generator stay flat — no `clamp()` there.** `hex_build_style_tokens_css()` writes the derived `--hex-{key}-size` as a flat copy of `--hex-{key}-size-desktop`, never a `clamp()`, even after a Theme Options save. `hex_build_fluid_clamp()` itself is left defined (still covered by its own tests) but is no longer called from the token-file build path — don't reintroduce a call to it there.
  5. **The `.hex-*` classes ARE fluid again, but under two hard constraints** — explicit instruction: *"now we have dedicated classes for each font variation. so now we can use all that classes in one clamp. but not theme options css. it should be somewhere else. but rule is dont use multiple clamp calculation functions. all css classes should use one function."*
     - **Exactly one shared `clamp()` calculation, never one per class.** Every `.hex-h1`…`.hex-meta` class only sets its own `--mobile-font-size`/`--desktop-font-size` (each `var(--hex-{key}-size-mobile/-desktop, {default})` — still Theme-Options-driven, per rule 1 above); one shared selector list (all eleven classes) applies the single `font-size: clamp(...)` rule. Never write a second `clamp()`/duplicate the formula for an individual class.
     - **The breakpoints are hardcoded and never touch Theme Options.** `--hex-static-breakpoint-s`/`-m`/`-l`/`-xl` (640px/960px/1200px/1600px — Small/Medium/Large/X-Large: Phone Landscape–Large Phones / Tablet Landscape–Small Laptops / Standard Desktops / Large Screens–High-Res Monitors) live as plain `:root` values in `site-theme.css` itself — not a schema field, never written to `theme-options.css`, not admin-editable. Distinct from Theme Options' own `--hex-fluid-breakpoint-s/-m/-l/-xl` (Global tab), which feeds the unrelated flat `--text-h1` chain in rule 4. Only S and XL feed the actual interpolation; M/L are declared for parity, unused by the formula (same pattern as the admin set).
  6. No `* 1px` bare-number trick in any of this project's own clamp() formulas — `--hex-{key}-size-mobile`/`-desktop` are already real px lengths (per rule 7 below), so the formula operates on lengths directly, the way `hex_build_fluid_clamp()` (PHP) already does. See `knoladge/fluid-typography-clamp.md` for the full history.
  7. **Every value in `site-theme.css` and its matching `hex_get_style_schema()` default must be `px` — never `rem`/`em`/`%`.** Explicit instruction: *"now change all values to px in css file. add rule always everything should be px only."* Applies to every length this project authors: font sizes, letter-spacing, line-height is exempt (unitless by design, not a length), margins, spacing scale, radius scale, icon sizes, button/form/card/table/alert/badge padding — all of it, always `px`. A letter-spacing `em` value converts using that same field's own **desktop** font-size (e.g. H1's `-0.02em` at a 40px desktop size → `-0.8px`) — em is relative to font-size, so this is a real (not approximate) conversion at that specific size, not merely a fixed 16px-root ratio the way `rem`→`px` is. Exception, and the *only* exception: Tailwind's own built-in framework defaults (`--spacing`, `--text-xs`/`sm`/`base`/`lg`/`xl`, `--container-*`, `--radius-xl`, the `@tailwindcss/typography` plugin's `.prose` internals, and Tailwind's responsive breakpoints) — those are framework-owned lines we never authored and don't override; this rule governs only what this project's own code writes into `site-theme.css`'s `@theme`/`@layer` blocks and `hex_get_style_schema()`'s defaults.
- **The Hexnity logo/brand color palette (`hexnity-*` in `assets/css/src/theme.css`) is admin-only** — explicit user correction: *"just use logo and colors only for admin pages. dont use it for theme."* The front-end build (`assets/css/src/front.css`) doesn't even import `theme.css`. Don't reintroduce the logo or `hexnity-*` classes to any front-end template without the user asking again.
  - Within the admin itself, `hexnity-*` is **not mandatory on every element** — explicit follow-up: *"u dont need to strict with logo colors."* The logo/`hexnity-900` sidebar background is the one place brand identity matters; everywhere else in the dashboard (buttons, links, active states, focus rings) uses Tailwind's `indigo` scale as the general accent. Don't force `hexnity-*` onto new admin UI just for brand consistency — pick whatever reads well, same as any other admin design decision.
- **Tailwind-in-wp-admin color gotcha**: WordPress core's own admin CSS is unlayered, and Tailwind puts every utility in a `@layer` — unlayered rules always beat layered ones regardless of specificity, so a plain Tailwind color utility (e.g. `text-white`) can silently lose to WP core's own `a { color: ... }`. If an admin-page color utility doesn't visually apply, this is almost certainly why — fix with Tailwind v4's trailing `!` important-modifier (`text-white!`), and verify `!important` actually landed in the compiled CSS before calling it fixed. See `knoladge/tailwind-cascade-layers-vs-wp-admin.md`.
